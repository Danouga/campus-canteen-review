# 09-部署改造与托管说明

> 版本：v1.0｜更新日期：2026-10-14｜记录本会话对「食间校园食堂共建网站」的全部改造与托管上线过程。

本文档记录一次完整会话中，将原本依赖 **MySQL（mysql2）+ sharp + 腾讯云数据库** 的原型，改造为可在 **WorkBuddy「发布为应用」免费托管** 的形态，并完成数据迁移、Bug 修复与上线验证的全过程。所有改动均已提交到本地 git 并部署上线。

---

## 1. 背景与目标

| 项目 | 说明 |
| --- | --- |
| 原始架构 | Node.js 原生 HTTP 服务 + MySQL（`mysql2`）+ `sharp`（图片处理）+ 邮箱验证码登录注册 |
| 目标 | 在 WorkBuddy「发布为应用」免费托管，做**小范围用户测试** |
| 核心障碍 | 发布沙箱**不提供数据库**、且**拒绝任何依赖 `mysql2` 的项目**（即使连公网 MySQL 也被拒，因为工具只检测依赖清单） |

结论：要让项目能在 WorkBuddy 免费托管，**必须把数据库层从 MySQL 改为沙箱内可独立运行的自带存储**，并移除 `mysql2` / `sharp` 依赖。

---

## 2. 改造总览

- **存储引擎**：MySQL → 零依赖的 **JSON 文件存储**（`node:fs`）。整站内容状态写 `data/app-data.json`，图片写 `data/media/<hash>`。
- **依赖精简**：移除 `mysql2`、`sharp`；仅保留 `nodemailer`（邮箱验证码）。
- **登录系统**：逻辑（`auth.mjs`）**一行未动**，仅把底层存储（`auth-store.mjs`）迁移到 JSON 实现。
- **数据迁移**：从腾讯云 MySQL 导出全部内容 + 管理员账号 + 15 张图片，作为种子随代码提交，空库自动注入。
- **修复两个线上 Bug**：登录 UI 不显示、发验证码「来源无效」403。
- **新增导出功能**：管理员可在管理工作台一键导出全部数据为 zip。

## 4. 关键逻辑说明

### 4.1 存储契约
`store.mjs` 把整库存为一份 `data/app-data.json`，顶层结构：
```
{ state: "<整站内容状态 JSON 字符串>", revision, media:{}, users:[], codes:[], sessions:[], rateLimits:[] }
```
- `state` 是**字符串**（前端 `repository.js` 用 `JSON.parse` 解析）。
- 图片二进制另存 `data/media/<64位hash>`，`media` 记录元信息。
- 进程内串行锁，避免并发写损坏。

### 4.2 种子注入（保证线上非空库）
`db.mjs` 在 `store.load()` 之后检测：若 `state` 为空，则从代码包内的 `seed-data.json` + `seed-media/` 注入（写 `app-data.json`、复制图片到 `data/media/`），日志输出 `已从种子恢复迁移数据：users=N, media=M`。这样无论部署平台是否忽略 `data/`，线上都能拿到真实数据。

### 4.3 缩略图降级
`resizeImage()` 优先 `import('sharp')`，失败或缺模块时返回 `null`，上层退化为返回原图，**不再因原生模块装不上而导致整站无法启动**。

## 5. 两个线上 Bug 的修复

### 5.1 登录系统「不显示」（只看到演示身份切换）
- 原因：`src/app.js` 中 15 处判断均以 `storageMode === 'mysql'` 作为显示真实登录 UI 的条件；改造后 `/api/status` 返回 `mode:'file'`，前端不识别，回落到老演示模式。
- 修复：服务端返回非 `local` 模式一律在前端映射为「服务器模式」，15 处判断自然生效。
- 影响：数据一直存在线上服务端，**只是身份系统 UI 没露出**；修复后右上角变为邮箱登录/注册。

### 5.2 发送验证码「来源无效」403
- 原因：原同源校验 `origin !== ${scheme}://${request.headers.host}`。WorkBuddy 反向代理会改写 `host` 头，浏览器真实域名 `Origin` ≠ 代理内部 `host`，被误判拦截。
- 修复：抽成 `assertSameOrigin(request, config)`，放行策略：
  1. 本地 `localhost` / `127.0.0.1`；
  2. 精确白名单 `AUTH_ALLOWED_ORIGINS`（`.env.local` 中配置线上域名）；
  3. WorkBuddy 托管子域 `*.app.workbuddy.host`；
  4. 或 `Origin` 与代理转发头 `x-forwarded-host` / `host` 一致。
- 验证：`shijian-canteen.app.workbuddy.host` 真实 `Origin` → 200；伪造 `evil.example.com` 仍 → 403（2026-10-14 检查发现旧校验过宽，现已改为精确来源白名单）。

## 7. 托管方法：WorkBuddy「发布为应用」

### 7.1 适用条件与限制
- 沙箱只暴露**一个公网 HTTP 端口**（服务需监听 `0.0.0.0`、读取 `PORT` 环境变量）。
- **不提供数据库 / 缓存 / 消息队列**；依赖 `mysql2`/`pg`/`redis` 等外部服务的项目会被拒绝上传。
- 本项目用自带 JSON 文件存储，不依赖外部数据库，故可正常发布。

## 8. 部署踩坑与注意事项（重点）

### 8.1 ⚠️ 必须先 `git commit` 所有改动
发布工具**只打包 git 跟踪的文件**，未提交 / 未跟踪（`git add` 过但未 commit 也不行）的文件**不会进沙箱**。本会话曾因环境变量未正确配置、`seed-*` 未跟踪或代码未提交，导致线上仍是旧代码 / 空库。秘密必须通过运行环境配置，不能通过提交 `.env.local` 解决。部署前只提交代码和不含敏感信息的配置示例。**禁止提交 `.env.local`、其备份以及真实授权码、密码、签名密钥；秘密通过托管环境配置。**

### 8.2 不能残留 `mysql2` / `sharp`
`mysql2` 会让发布工具判定「需要外部数据库」而拒绝上传；`sharp` 是原生模块，沙箱 `npm install` 可能失败。源码、脚本、测试、依赖清单中**任何 `import mysql2` 都要清理**。本会话已删除 4 个含 `mysql2` 的文件并将两者移出 `package.json`。

### 8.3 监听地址与端口
必须用 `0.0.0.0`（不是 `127.0.0.1`），并读取 `PORT` 环境变量；本地变量可通过被 Git 忽略的 `.env.local` 注入；托管环境应单独配置秘密，禁止提交本地秘密文件。

### 8.4 沙箱数据**没有永久承诺**
数据存在托管的沙箱文件系统（`data/app-data.json`）。WorkBuddy 对沙箱数据卷保留多久**没有公开承诺**（不像它自家云服务明说 15 天，但也非保证永久）。建议：
- 上线后**立即用管理工作台「导出全部数据」** 下一份到本地；
- 后续改动重发布前也可先导出，避免覆盖丢失。

### 8.5 链接长期有效
分享链接本身不会自动过期，由你在「设置—数据管理—应用」中管理，随时可「取消发布」下线。**只要账号在、不主动取消，链接就一直在线。**

### 8.6 「云服务未启用」不是错误
本项目用自带存储、未接 WorkBuddy 云服务，故应用管理面板显示「云服务未启用」、用量统计为空。这**不影响线上运行**，只是平台用量面板不采集自实现存储的数据。
