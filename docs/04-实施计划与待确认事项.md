# 实施计划、测试与待确认事项

版本：v0.1｜日期：2026-10-02

## 1. 阶段计划

以下按“1 名前后端开发者 + 兼职设计/测试 + 1 名内容运营负责人”估算，团队经验和学校接口会显著影响进度。若只有一名兼职开发者，应顺延；若已有可用店铺数据，可缩短录入时间。

| 阶段 | 参考周期 | 交付物 | 退出条件 |
| --- | --- | --- | --- |
| 0. 两校区骨架与规则 | 1–2 周 | 确认版 PRD、两校区和食堂清单、营业时间字段、规则阈值、管理员 | 校区与食堂可建立，店铺资料允许为空 |
| 1. 交互与基础工程 | 1–2 周 | 空白页与加号原型、设计规范、仓库/部署/数据库基础、管理员受控登录 | 手机端共建申请路径可走通 |
| 2. MVP 共建与管理 | 3–5 周 | 两校区目录、空白入口、共建初审→暂示/直接固定、管理员编辑/删除、菜品价格和营业时间、评论屏蔽词筛选 | 关键共建用例通过；可内部试用 |
| 3. V1 社区与投票 | 3–6 周 | 学校接口申请结果后的正式登录、推荐票与周榜、评论互动、美食贴、收藏、奖励票、通知、规则化推荐 | 身份、投票与审核用例通过；可控制范围开放 |
| 4. 试运行与修正 | 2–4 周 | 用户共建数据核查、性能/安全检查、运营手册、试点反馈 | 风险门槛满足；可决定扩大开放 |

合计约 10–19 周是粗估，不含学校授权、域名备案或登录接口对接等待。若学校接口无法及时取得，可先交付内部 MVP；公开投票与投稿时间需要另行安排。

## 2. 工作分解与依赖

1. **资料与规则**：先建立两个校区及食堂骨架、营业时间字段和资料来源规则；店铺不要求初始录入。
2. **账号与权限**：管理员先有受控登录；普通用户凭证待学校接口申请结果决定，公开发帖和投票依赖此步骤。
3. **目录与详情**：空食堂和缺失字段显示加号；用户申请新店或补充资料，管理员可直接新增、编辑、下架。
4. **推荐票与榜单**：周周期、票额、流水、幂等、同票规则、历史快照；应先用测试数据做跨周验证。
5. **社区互动**：评论/帖子、赞同/反对、收藏、举报、隐藏与申诉；审核后台同期完成。
6. **用户共建**：申请类型、图片隔离、管理员初审、暂示/直接固定、回退、冲突审查、奖励联动；先实现初审和管理员直接处理，V1 再接互动奖励。
7. **推荐与运营**：本周热门、低参与店轮换、通知、监控、后台配置；在基础数据与用户互动已有样本后校准。

## 3. 测试计划

| 层级 | 重点用例 |
| --- | --- |
| 规则单元测试 | 票额计算、日期/周边界、奖励阈值、隐藏阈值、共建状态迁移、同票排序 |
| 数据库/集成测试 | 并发投票、幂等重试、重复奖励、任务补跑、资料回退、权限隔离 |
| 端到端测试 | 两校区空白食堂添加店铺申请；管理员暂示/固定/删除；内部测试用户投票、评论、发帖；审核员处置与申诉 |
| 内容与安全测试 | XSS、越权编辑、恶意文件、超大图片、刷赞/刷票频率、隐私信息暴露 |
| 试运行检查 | 小屏适配、图片加载、搜索无结果、关店显示、举报响应、备份恢复 |

需要准备跨周和跨天的“固定时钟”测试环境，不能等到真实周一才验证。测试账号和测试票不得混入公开榜单。

## 4. 数据准备模板

MVP 只需建立两个校区和已知食堂，可以没有任何店铺。食堂需有营业时间字段，未知则标“待补充”；店铺、菜品、价格、照片和个别店铺延时关门信息由共建逐步补齐。每条正式资料应能追到来源、审核人和更新时间。管理员可直接填写或纠正，删除以可恢复下架处理。

## 5. 运营与治理准备

- 指定内容审核和店铺资料审核负责人及替补，约定申请初审频率与严重举报响应路径。
- 建立可维护的评论屏蔽词库，区分“直接拦截”和“转人工复核”，记录误判申诉；词库不替代举报和管理员处理。
- 发布社区规则：禁止人身攻击、隐私曝光、虚假信息、刷票互赞、未经许可图片与隐性广告；说明反对票只是复核信号。
- 明确申诉流程和处置记录；对店铺经营者的事实纠错提供渠道，同时保持用户评论独立。
- 上线前准备用户协议、隐私告知、图片上传声明、数据删除/账号注销流程，并按实际运营方式核对备案等要求。
- 每周观察新增店铺、参与人数、有效投票、隐藏内容、申诉结果、共建固定准确率与审核积压，按数据调整阈值。

## 6. 试点发布检查表

- [ ] 学校/校区、试点食堂和运营主体已确认；平台名称不造成“学校官方”误认。
- [ ] 两校区食堂骨架、空白加号入口、菜品价格和食堂营业时间字段可用；图片来源和授权可追溯。
- [ ] 管理员受控登录、共建初审、暂示/直接固定、直接编辑/下架与审计通过验收。
- [ ] 公开投票和投稿前，正式用户身份方案、退出、封禁、跨周、榜单、评论与举报流程通过验收。
- [ ] 评论/帖子隐藏与申诉可用；后台有人负责处理。
- [ ] 奖励票不会重复发放；异常账号处置和冲正有审计记录。
- [ ] 共建暂示与正式资料区分；高影响变更需人工核验；版本可回退。
- [ ] 隐私告知、用户协议、内容规则和上线手续核对完成。
- [ ] 数据库备份与恢复演练通过；任务失败有告警。
- [ ] 手机端和常见浏览器已检查；错误页、空状态和慢网速可用。

## 7. 待用户/学校确认的决策清单

| 优先级 | 问题 | 当前文档假设 | 影响 |
| --- | --- | --- | --- |
| 必须 | 两校区各有哪些食堂，名称和位置如何写？ | 已确定两校区；食堂清单待补 | 空白目录骨架 |
| 必须 | 谁是运营主体，谁有权审核与处理申诉？ | 有指定管理员和审核员 | 能否开放用户内容 |
| 后续依赖 | 学校是否提供登录接口、凭证如何设计？ | 先申请接口；MVP 不定普通用户凭证 | 公开投票、投稿和共建开放时间 |
| 必须 | 用户上传图片如何确认来源与授权？ | 提交时声明并由管理员核验 | 图片公开展示 |
| 已确认 | 推荐票每日与同店上限 | 每天 1 张基础票；奖励票保留；同店每天最多 3 张 | 票钱包与数据约束 |
| 高 | 评论/帖子/共建的阈值多少？ | 文档中的 10/5/8 等为建议值 | 冷启动与误伤率 |
| 已确认 | 用户申请如何进入正式资料？ | 管理员先审核，再暂示或直接固定；管理员可直接编辑/删除 | 共建流程与后台 |
| 中 | 是否允许游客查看帖子和评论？ | 可以浏览，互动需登录 | 内容传播范围 |
| 已确认 | 评论是否允许回复、多层回复？ | 暂不开放 | 降低首版工作量 |
| 已确认 | 是否展示菜品价格与营业时间？ | 展示菜品价格、食堂营业时间及个别店铺延时关门 | 共建字段与更新时间 |
| 高 | 评论屏蔽词库从何而来、命中后如何处理？ | 管理员维护；可拦截或转人工复核 | 误判率与运营负担 |
| 中 | 是否预留商家认领入口？ | V1 后评估 | 权限与争议处理 |

可先按已确认规则建立两校区空白目录和管理员流程。学校登录接口与词库来源仍需后续确定；建议阈值可随试点数据调整，但须记录规则版本和生效时间。

## 8. 后续功能立项条件

| 功能 | 启动前验证 |

| 三维食堂与告示牌 | 有可用平面/三维资料和授权、手机性能可接受、告示牌审核与定位规则已定义 |
| AI 推荐 | 有足够真实互动数据、能比较推荐效果、隐私告知和用户控制方案已明确 |
| 微信小程序 | 网页试点稳定、后端接口可复用、小程序主体与发布流程明确 |

这四项可先在导航或个人中心预留“规划中”入口，点击后显示说明页；不实现虚假的可操作按钮或尚无处理能力的申请表单。
