# 项目立项与可行性分析

版本：v0.3｜更新日期：2026-10-13

当前已形成可运行的内部演示 MVP：目录、评论和富文本帖子、标签与共建互动、推荐票和来源明细、积分占位、审核员与管理员分工、图片描述、MySQL 和媒体分离已实现。正式学校登录、收藏、举报申诉、完整审计与公开部署仍是后续阶段。以下运营指标和上线要求是规划门槛，不是已达到的事实。

## 1. 项目概述

### 1.1 背景与问题

学生找饭店通常依靠口耳相传或分散的社交帖子，信息容易过时；新店、关店、菜单变化也缺少统一维护入口。本项目以“食堂—店铺—菜品”为目录，让学生查看位置与图片、发表评论、投每周推荐票、发布美食贴，并共同纠正店铺资料。

### 1.2 目标与衡量方式

| 目标 | 试运行建议指标（待按学校规模调整） |
| --- | --- |
| 能共建 | 两校区各食堂均有明确的“添加店铺/补充信息”入口；提交申请可进入管理员队列 |
| 信息可信 | 已审核资料显示来源和更新时间；关店/搬迁争议有处理记录 |
| 有真实互动 | V1 开放公开互动后的试点期，每周至少 30 条有效评论、20 张推荐票；排除管理员测试数据 |
| 能治理 | 举报与申诉均可进入后台队列；严重内容有人工处置路径 |
| 系统可用 | 试点期核心页面可用性目标 99%；统计方法由监控日志定义 |

这些是试点门槛，不是已有事实或对外承诺。项目采用“空白目录起步”：只建立两个校区与已知食堂的骨架，店铺由用户申请或管理员直接添加；初期搜索、榜单和推荐可能为空，界面必须清楚引导共建。后续若与老师合作推广，可再设定覆盖率目标。

### 1.3 用户与利益相关方

- 学生/教职工：找店、评价、投票、发布内容、申请修改资料。
- 店铺经营者：核对自己的基础信息、反馈错误内容。后续可评估“经营者认领”，但不能直接改写用户评价。
- 管理员/内容审核员：维护目录、处理举报与申诉、审查图片和共建申请、设置阈值、查看审计日志。
- 学校相关部门：确认场地信息使用、校园标识/地图/图片使用，以及试点推广和运营责任。

### 1.4 关键前提

1. 学校有两个校区；校区和食堂名称由项目发起人建立，店铺资料不要求预先录入。
2. 首版为中文响应式网页。学校登录接口能否申请到尚不确定，MVP 不定登录凭证和对接方式；公开互动需要能识别用户的账号能力，开放时间受此依赖约束。
3. 所有用户共建申请先经管理员或审核员审核，可暂时展示或直接固定；只有管理员可直接维护目录。当前有部分状态、时间与应用快照，完整操作人审计尚未实现。
4. 评论先经过演示词库筛选；人工隐藏、恢复和移除已有入口，举报申诉和正式词库维护尚未实现。词库无法判断全部语境，需保留人工处置能力。
5. 先小范围邀请测试；公开上线前核实部署地、备案、隐私和内容治理要求。

## 2. 范围和优先级

| 阶段 | 包含 | 暂缓 |
| --- | --- | --- |
| 当前 MVP | 两校区目录、详情路由、共建初审与暂示固定、管理员直接维护、审核员角色、图片压缩与描述、评论帖子态度、阈值隐藏、推荐票周榜及明细、消息已读、积分占位、MySQL 和媒体分离 | 正式学校身份、收藏、举报申诉、完整审计、积分兑换 |
| 正式试点 | 可信身份与会话、服务端内容处理、分表与并发、后台任务、异常互动识别、运营流程 | 依学校接口和试点负责人确定时间 |
| 后续扩展 | 低参与探索、收藏编辑、积分兑换、三维、AI、小程序和赞助 | 当前仅保留部分规划说明 |

当前已完成可浏览、可管理的目录、社区与票制演示；若学校登录接口迟迟未获批准，可用仅限内部测试的账号验证互动规则，但不应把公共匿名投票作为正式方案。

## 3. 可行性评估

### 3.1 技术可行性：可行，难点在规则一致性

目录、评论、帖子、图片上传和榜单均可用常见 Web 技术实现。复杂处是每日票额、每周归档、奖励票、内容隐藏、共建信息“暂时展示→固定→退回”的并发和追溯。建议使用关系型数据库、事务、唯一约束、不可变流水和定时任务；后台统计可异步生成，但用户投票结果须立即一致。当前 MySQL 用一行 JSON 和事务锁保存业务，图片二进制已分离；独立业务表、完整流水审计和后台任务属于下一阶段。具体方案见[技术与数据方案](./03-技术与数据方案.md)。

### 3.2 运营可行性：有条件可行

空白目录降低了单人录入成本，但冷启动时店铺列表、榜单和推荐会为空。应在两个校区的食堂页放醒目的加号入口，允许申请新店及补全资料；申请先由管理员或审核员检查，再决定进入暂时展示或直接固定。管理员可直接编辑或删除错误资料。照片、菜单、价格、食堂营业时间和店铺延时关门信息需显示更新时间与来源。评论由词库先筛选，命中时拦截或转人工复核；反对票和词库都不能替代事实裁决。若与老师合作推广，用户招募问题可能缓解，但审核工作量也会增加。

### 3.3 经济可行性：小范围试点可低成本启动

主要成本是开发与管理员审核人力，其次为服务器、数据库备份、对象存储/图片流量、未来可能的登录服务、域名与监控。空白起步省去批量录入，但每条用户申请仍需审核。建议先用低量级方案验证；正式预算按注册人数、日活、照片数量、审核申请量和保留期重估。

### 3.4 合规与授权可行性：需上线前核对

本节保留早期调研链接和规划提示，本次功能文档更新未重新做法律或备案审核；应按届时实际主体、部署和功能核对。

- 仅收集登录与运营必要的信息，明确用途、保存期限、删除与申诉渠道。个人信息处理应遵循《个人信息保护法》有关告知、最小必要等要求。[中国人大网《个人信息保护法》](https://www.npc.gov.cn/WZWSREL25wYy8vLy8vL2MyL2MzMDgzNC8yMDIxMDgvdDIwMjEwODIwXzMxMzA4OC5odG1s)
- 公开评论、回复、点赞等功能需要服务规则、内容管理、举报与申诉机制，实际适用范围及运营义务需按上线方式核对。[国家网信办《互联网跟帖评论服务管理规定》](https://www.cac.gov.cn/2022-11/16/c_1670253725725039.htm)
- 若在中国境内以网站形式提供非经营性互联网信息服务，应核对备案要求与部署主体；上线前以接入服务商和主管部门要求为准。[工信部《非经营性互联网信息服务备案管理办法》](https://www.miit.gov.cn/gyhxxhb/jgsj/cyzcyfgs/bmgz/xxtxl/art/2024/art_84a0cfa0ebd049bbbe751dca9a008e56.html)
- 后续若引入个性化算法、广告或赞助，应重新评估展示规则、告知和标识；规则化排序也应向用户说明主要依据。[国家网信办《互联网信息服务算法推荐管理规定》](https://www.cac.gov.cn/2022-01/04/c_1642894606364259.htm)

本节是产品规划提示，不代替针对具体运营主体和部署方式的法律意见。

## 4. 风险登记

| 风险 | 发生可能/影响 | 缓解与触发动作 |
| --- | --- | --- |
| 店铺资料失真 | 高/高 | 申请先经管理员审核，显示更新时间与共建来源；管理员可编辑/删除并留痕 |
| 空白目录冷启动 | 高/中 | 两校区食堂页设置加号入口和共建说明；与老师合作推广后再评估覆盖率 |
| 刷票/互赞换奖励 | 高/高 | 一人一票额账本、反作弊频控、同设备/IP 异常提示、奖励上限、撤销奖励流水；人工复核异常榜单 |
| 反对集火误伤内容 | 中/高 | 达阈值先隐藏待审，保留申诉；禁止作者自投，显示处置原因与时间 |
| 不当内容与隐私泄露 | 中/高 | 发布前提示、举报、敏感内容人工审核、图片元数据清理、删除/封禁流程 |
| 共建自动固定错误事实 | 中/高 | 高影响申请（关店、搬迁）优先人工核验；固定后可回退，记录版本 |
| 冷启动缺少内容 | 高/中 | 先建立两校区食堂骨架和加号入口；与老师合作推广并引导用户提交店铺申请 |
| 学校合作或图片权属不清 | 中/高 | 确认名称/标识/地图/照片许可；未经授权不宣称官方平台 |
| 团队持续运营不足 | 中/高 | 指定负责人和响应时限；无法保障时限制公开发帖范围 |

## 5. 建议的立项结论与门槛

项目适合以两个校区的空白食堂目录做网页试点。开放公开互动前需具备：①明确的管理员审核与申诉负责人；②可识别用户且能防重复投票的登录方案；③投票与奖励流水可追溯；④隐私告知、用户协议、举报入口和部署手续核对完成；⑤主要业务流程通过验收。与老师合作后可再扩大推广。三维、AI、小程序和赞助先预留入口，待试点结果明确后决定投入。
